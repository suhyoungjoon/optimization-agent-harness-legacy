# 레가시 I/F 수용 영향도 분석

검토 기준: `suhyoungjoon/optimization-agent-harness` main `de3e755` (2026-10-10, PR #31 머지), 테스트 299개 통과 상태. 작성일 2026-10-15.

## 결론

레가시 I/F 10종 중 대부분은 구조 변경 없이 `domains/dispatch/` 안에서 수용할 수 있다. 공통 코어(`core/`)는 작업자·지시서·지점 같은 도메인 용어를 전혀 모르게 짜여 있고, `core/interfaces.py`의 `DomainPack` 메서드 시그니처도 그대로 유지된다.

구조 변경이 필요한 곳은 세 군데다: 실데이터(레가시 형식) 로딩, 할당취소·반송·이관 같은 이벤트 흐름, 운영 데이터 정정 개선안(선택).

## 레가시 I/F 목록 (참고)

1. 접수 (요청/반송/완료/작업이관): 진행관리, 작업이관, 승주 긴급요청
2. 일자별 작업자 시간역량 (시간역량이력 X): 개통스케쥴링할당(역량등록, 역량취소), 개통/AS 스케쥴링(M), 일자별시간역량(저장, 역량일괄등록), 표준작업시간 자동생성
3. 일자별 작업자 관할지역: 일자별지역역량(관할지역복사, 저장, 삭제), 작업자관할지역관리(저장, 삭제)
4. 일자별 작업자 표준작업시간: 역량관리기준정보(기본정보 - 표준작업시간일괄등록, 저장)
5. 기술역량: 기술역량(저장, 삭제), 작업자기술역량관리(저장, 삭제)
6. 할당이력: 할당(zossmcom22022), 할당취소(zossmcom22020)
7. 관리유형: 역량관리기준정보(기본정보 - 저장)
8. 할당제한반복일정 → 작업자 시간역량 N으로 전송
9. 근무시간 → 줄어드는 근무시간만 작업자 시간역량 N으로 전송 (당일 포함 이후 건)
   - 09~18 → 10~18: 09~10시 N 전송
   - 09~18 → 09~17: 17~18시 N 전송
   - 10~18 → 09~18: 연동 안 함
10. 구성원: 작업자/작업그룹구성원관리
11. (제외) 작업일자별역량 (일자별 휴가/근무/비가동 관리)

## 구조 변경이 필요한 곳

| 항목 | 지금 구조 | 바뀌는 범위 | 시점 |
| --- | --- | --- | --- |
| 실데이터(레가시 형식) 로딩 | 데이터셋은 `(seed, faults)`만 저장하고 매번 `pack.generate()`로 재생성 (`datasets` 테이블, `api/main.py` 3곳, `core/evaluation/runner.py`) | 계약에 `load(source)`류 추가, 데이터셋 테이블에 원천 정보 추가 → 코어·계약 변경 | 실데이터를 쓸 때만 |
| 할당취소·반송·이관·진행관리 (#1, #6 취소) | 항목 목록 고정(`items()`), 항목당 결정 1회, 상태 4종 | 상태 값, 하네스 러너, 지표 모두 변경 | 가장 큰 변경. 로드맵으로 |
| 운영 데이터 정정 개선안 (선택) | 개선안 종류는 `params`, `spec` 두 가지 | `core/improvement`에 새 종류 추가 | 표준작업시간·역량 정정 제안을 넣을 때만 |

## I/F별 영향도 (도메인 팩 안에서 수용)

핵심 차이: 지금 모델은 작업자 역량이 "모든 날 같은 값"인 정적 모델이고, 레가시는 일자별·시간대별 Y/N 역량이 중심이다.

| I/F | 규모 | 영향 파일 | 비고 |
| --- | --- | --- | --- |
| #2, #8, #9 일자별 시간역량 | 중 | `models`(Worker.available → 날짜별 구간 목록), `generator`, `rule_engine`(validate, `_best_slot`, 미할당 사유), `tools`(get_worker_schedule), `analysis`(worker_stats, demand_by_hour), `metrics`(가용시간 합), `pack.subset`, `faults.yaml`(P3), `domain-spec.md`, `web/src/domains/dispatch/DispatchMap.tsx` 1줄, 테스트 | `.available` 사용처 약 40곳. 하루 안에 비는 구간이 생기면 `_best_slot`이 구간별로 돌아야 함. #8, #9는 시간역량 N으로 내려오므로 생성 규칙만 추가 |
| #4 작업자별 표준작업시간 | 중 | `duration_min(order, params)`이 작업자 인자를 받게 변경 → validate, 일정 계산, metrics, analysis, `get_order` 도구 | 작업소요가 지시서 속성 → 지시서×작업자. `params.duration`은 기본값 역할 |
| #3 작업자·일자별 관할 | 중 | `models.distance_outside`(지금은 `w.branch` 경계 기준), `stage_slots`, `actual_stage`, `area_zone` 차원 정의, 지도 화면 | 관할 단위에 따라 경계 데이터 추가 필요 |
| #6 기할당 건 (취소 제외) | 중 | Instance에 고정 배정 추가, `solve`·`schedules_from`·`validate`가 미리 채운 일정에서 시작 | "이미 찬 일정"으로만 다루면 도메인 안에서 끝남 |
| #10 작업그룹 | 소 | Worker 속성, `dimensions.yaml`, 후보 범위를 그룹으로 할 경우 `eligible_workers` | 코어 집계는 차원 추가만으로 대응 |
| #5 개통/AS 역량 | 소 | `eligible_workers`, validate 규칙 1개, `violation_rules` | |
| #7 관리유형 | 소 | Worker 속성과 차원 | 배정 규칙에 영향이 있으면 규모 커짐 |
| #1 긴급 여부 (흐름 제외) | 소 | Order 필드, 차원, 처리 순서(`items()`, `solve` 정렬) | 반송·이관 흐름은 구조 변경 항목 |

#11은 범위 밖이지만 #2 일자별 시간역량으로 하루 전체를 N 처리하면 같은 효과를 낼 수 있다.

## 같이 알아둘 점

- 재현성: 데이터를 seed로 다시 만드는 구조라 생성기를 바꾸면 기존 실행 결과·시연 번들·실험 문서 수치가 같은 데이터셋 ID로 다른 데이터를 가리킨다. 그래서 별도 레포에서 진행한다.
- L0 비용: L0은 인스턴스 전체를 프롬프트에 넣으므로 일자별 역량이 들어가면 토큰 비용이 늘어난다.
- 계약 유지: 위 변경 모두에서 `DomainPack` 시그니처는 유지되고 도메인 모델(`Worker`, `Order`, `Instance`)만 바뀐다.
- 결함 패턴 후보: #9의 비대칭 규칙(ex3)은 일할 수 있는데 역량이 N으로 남는 "숨은 역량"을 만든다.
  - P5 근무시간 연장 미반영 (1단계에서 구현)
  - P6 반복 제한일정이 피크와 겹침
  - P7 관할지역 복사 누락

## 1단계 반영 결과 (#2, #8, #9 + P5)

- `Worker.available`은 기본 근무시간으로 두고, 일자별 시간역량 `Worker.capacity`(날짜 → Y 구간 목록, 근무시간과 다른 날만)를 추가했다. 판정은 `windows(day)`로 한다.
- 생성 규칙(`dataset.yaml` `capacity`): #8 할당제한반복일정(작업자 10%, 2~3일마다 60~120분 N), #9 근무시간 축소(작업자 10%, 변경일부터 줄어든 60분만 N, 늘어난 쪽은 연동 안 함).
- 시간 모델: 희망시간은 정시(1시간 단위), 약속은 `params.appointment.slot_min`(60분) 방문창. 매칭 허용오차 `matching.time_window_min`은 희망 시간대와 약속 시간대의 차이로 판정하며 `[0, 60, 120]`으로 바꿨다(params version 2).
- 1시간 방문창은 배정 여지가 커서 결함이 드러나도록 하루 지시서를 150건에서 185건으로 늘렸다 (seed 42 규칙 agent 기준 배정률 95.7%, P1 B지점 9~10시 실패 1.7%→21.6%).
- P5는 A지점 작업자 70%(7명)의 09~10시 시간역량을 N으로 남긴다. 미할당보다 A지점 09시 고객이 10시 이후로 밀리는 현상으로 드러나고(seed 42 기준 A지점 09시 희망 시간대 약속 비율 78%→25%), 정답표는 구간 {A, 09시} + 해당 작업자 + `worker_stats` 근거(근무시간 vs 시간역량 요약)다.
- 같은 seed라도 생성 데이터가 바뀌었으므로, 이 레포의 기존 실행 결과·시연 번들·실험 문서 수치는 이전 데이터 기준이다.

## 2단계 반영 결과 (#5, #10)

- #5 개통/AS 역량: `Worker.work_types`(install·repair 중 가능한 것). 매체 기술과 독립이며, 기본 데이터는 둘 다 가능 85%, 개통만 10%, 장애(AS)만 5% (`dataset.yaml` `workers.work_types`).
- 후보 필터 순서는 지점 → 매체 기술 → 개통/AS 역량 → 자격. 역량이 없으면 미할당 사유 `NO_WORK_TYPE`, 잘못 배정하면 필수조건 위반 `work_type_required`.
- #10 작업그룹: `Worker.group`(지점당 2개, 5명씩, 예: A1). 작업자 속성·분석(`worker_stats`의 group 필터)으로만 쓰고 후보 범위는 지점 그대로.
- 결함 패턴은 추가하지 않았다. seed 42 규칙 agent 기준 배정률은 95.7%에서 94.6%로 내려갔고, 한쪽 전담 작업자 때문에 기술·역량을 다 갖춘 자격자가 없는 경우가 생겨 `NO_CERT`가 13건 나온다.
